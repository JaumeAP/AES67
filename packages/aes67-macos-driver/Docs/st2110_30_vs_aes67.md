# SMPTE ST 2110-30 vs AES67 — what differs, and where this driver stands

Research notes, August 2026. Companion to
`audio_over_ip_standards_landscape.md`.

ST 2110-30 is not a second standard to implement alongside AES67. It is
AES67 with additional constraints: same RTP transport, same packet
construction, largely the same signalling. The differences below are all
restrictions, not new mechanisms.

## 1. Conformance levels — the structural difference

AES67 has **one** mandatory configuration. ST 2110-30 has **six conformance
levels**:

| Level | Channels/stream | Packet time | Sample rate | Bit depth |
|---|---|---|---|---|
| **A** (mandatory) | 1–8 | 1 ms | 48 kHz | 16 / 24 |
| **B** | 1–8 | **125 µs** | 48 kHz | 16 / 24 |
| **C** | up to **64** | 125 µs | 48 kHz | 16 / 24 |
| CX variants | 32 @ 96 kHz, or 64 @ 48 kHz | 125 µs | 48 / 96 kHz | 16 / 24 |

**Level A is exactly AES67's mandatory configuration.** Anything meeting
Level A meets AES67's baseline and vice versa.

## 2. RTP timestamp offset — the one hard behavioural difference

> AES67 streams may have a random offset for their RTP stream clock; in
> ST 2110-30 that offset must be **0**.

This driver initialises `timestamp_ = 0` in `RTPTransmitter::start()`
(`NetworkEngine/RTP/RTPTransmitter.cpp`), so it already satisfies the
ST 2110-30 requirement. Worth noting that this was not a deliberate
ST 2110-30 decision — AES67 alone would have permitted a random offset, and
nothing in the code says the zero is load-bearing. Anyone tempted to
randomise it for AES67 reasons would silently break ST 2110-30 conformance.

## 3. Where this driver already meets Level A

- Packet time defaults to 1 ms — `SDPParser.h`, `SDPSession::ptime`
- L16 and L24 encodings — `SDPParser.cpp`
- 8-channel flows — `StreamChannelMapper::kMaxChannelsPerFlow`, and
  `StreamManager::createTxStreamFlows()` splits anything wider
- 48 kHz supported
- RTP timestamp offset of 0 — see above

## 4. Where this driver goes beyond Level A

Not defects — being wider than the mandatory minimum. But a strict
ST 2110-30 receiver will only accept the subset:

- **Sample rates.** `AES67Device::kSupportedSampleRates` declares eight
  rates up to 384 kHz. ST 2110-30 Level A permits **48 kHz only**; 44.1 and
  96 kHz fall outside the mandatory level (96 kHz appears in the CX
  variants). Streams at anything but 48 kHz will be refused by a receiver
  holding to Level A.
- **AM824.** `SDPParser.cpp` accepts `AM824` alongside L16/L24. That
  encoding belongs to **ST 2110-31**, not -30.

## 5. What's missing for Level B or C

**A configurable transmit packet time.** Levels B and C both require
125 µs, and `RTPTransmitter` currently hard-codes 1 ms
(`intervalUs = 1000`). The receiver side already reads `ptime` from the SDP
and adapts — the asymmetry is transmit-only.

This is the same gap already recorded in the compatibility review in the
`llibreries` repo (`aes67_driver_compatibility_review.md`), where it was
noted for RAVENNA's 1–192 sample-per-packet range. The same fix serves both:
one configurable transmit ptime unlocks RAVENNA's flexible packet sizing and
ST 2110-30 Levels B/C at once.
